# Wolf 数据库读取与金币 MVP

## 当前实现：MY 实时读取已由用户验收，写入待验收

旧版按日文名称定向读取已替换为通用数据库读取与独立语义层。原生层不解释金币，不要求表名为パーティー情報。

链路：GameEngineAdapter.database → preload/IPC → 当前会话 wolfDriver → injector stdin → 双向 Named Pipe → DLL DatabaseReader → 认证 RPC 响应 → 数据库浏览器。主进程金币规则通过同一接口查目录，并在首次连接或 CTool 获得焦点时读取单元格，再经 telemetry.gold 显示。

- 分页浏览用户数据库、可变数据库、系统数据库的表、字段、记录及数字/字符串值。
- 目录每次最多 8 张表，每张返回前 64 个字段；记录每页最多 10 行、16 列，可继续翻列。字符串有长度限制，不是完整导出。
- 可变数据库的数字单元格可“设为金币”：绑定动作本身不修改游戏；控制台另有明确的应用按钮写入绑定字段。
- 无任意地址读写 API、无功能 Hook。仅开放绑定金币数值修改；失联及会话结束清理请求和遥测，读取失败显示 unavailable/null，不伪造 0。

## 金币和道具语义

金币自动规则使用可变数据库、单行表、金币字段别名、队伍表名别名及至少 4 个编号成员数字字段的组合证据。只选择唯一强候选；多义或目录读取不完整时不自动决定。弱候选供确认，自定义名称仍可浏览和手动绑定。

Wolf 基本系统有金币/道具/装备的数据设计，但作者可修改或不使用基本系统，不存在所有作品强制一致的金币槽位。官方旧例使用可变数据库类型 3，MY 为类型 6，因此不能固定表编号或仅凭同名字段判断。
参见[基本系统说明](https://silversecond.com/WolfRPGEditor/Guide/BASE_001.html)、[金币操作示例](https://silversecond.com/WolfRPGEditor/Guide/PRO_003.html)、[数据库说明](https://silversecond.com/WolfRPGEditor/Help/05database.html)。

道具/武器/防具目前只有数据库分类提示和原始记录浏览，定义列表不等于玩家持有列表。标准化背包数量、装备槽、通用变量组及其修改尚未实现。

## 统一修改器与金币写入

Wolf 使用独立的 `WolfCheatMenu` 标签页，展示游戏控制台、游戏数据库；不伪造完整 overview 或开放未适配的快捷键。Wolf 的 `WolfGoldEditor` 点击“应用到游戏”提交；MV/MZ 保持原有主页金币输入和失焦提交行为，两者不再共享控件或交互逻辑。

写入链路：WolfGoldEditor → GameEngineAdapter.setGameGold → preload/IPC → 当前会话 → goldMonitor.write → goldwrite RPC → DLL。

- DLL hello 的 goldWriteProtocol=1 单独协商写入能力，旧 DLL 仍只读。
- 主进程只允许当前选中的金币来源，并核对用户编辑开始时的旧值；浏览接口拒绝写操作。
- 原生只允许可变数据库数字字段、非负 int32；重新解析结构，检查可写内存及对齐，不修改页保护。InterlockedCompareExchange 比较旧值后写入，再通过数据库结构回读。
- 不重试写请求。响应丢失或写后回读失败不能证明未写入，必须先核对游戏。
- 这是后台线程的受保护单值写入，不是游戏主线程事务。结构重查、SEH 和比较交换不能完全消除读档时的并发重分配风险；不要在读档或场景切换中修改。后续安全点调度仍需专门适配。
- 修改的是运行内存，不主动保存存档，也不强制刷新游戏菜单；必要时关闭并重新打开金币菜单。

复用范围：标签页、Adapter、会话、金币编辑器已复用。MV/MZ 物品表的统一 id/name/playerHasCount 展示可在 Wolf 完成库存映射后复用；角色页所需的等级、职业、属性和装备关系尚无映射，战斗/移动开关不能直接复用。

## 内存定位与旧实现错误

在主模块可执行段唯一匹配数据库初始化指令，解析重定位后的根指针及三类数据库；不搜索当前金额，不固定绝对地址，不使用哈希限制启动。

MY x86 已观察布局：数据表步长 0x54，元信息步长 0xe8，记录步长 0x24。元信息 **+0x60 为记录名向量，+0x78 为字段名向量**。旧实现将它们写反，旧合成夹具也重复该错误；旧测试通过不证明真实读取成功。新夹具独立构造“1 条记录、7 个字段”回归。

代码还包含 MTool 分析所得 0x20/0xe4 布局候选，须通过结构检查，尚无真实样本验证。字符串布局及三类数据库覆盖仍需更多样本。特征或结构检查失败保持不可用，不猜地址。当前仅 x86，不宣称覆盖全部 Wolf 2.x/3.x。

## MY 既有证据（非新 DLL 端到端结果）

GamePro.exe 版本资源 3.595.2025.503，x86。可变数据库 99 张表；type 6 / row 0 / field 0 为当前金币，type 95 也有金币字段。既有只读探针初次观察两处均为 5000；用户报告消费 11000 → 9500 后，探针读取 type 6 为 9500，type 95 仍为 5000。未采样到 11000。游戏路径、表编号、金额均不写进产品识别配置。

## 验证与验收

2026-09-13 用户确认 MY 数据库已连接，游戏内改变金币时工具随之改变；截图显示 8500。这是新读取链路的用户验收，不扩大到其他游戏，也不代表本轮写入已实测。

本轮验证：26 项 Wolf 测试通过；原生合成内存完成 5000→9500 写入及旧值冲突/非法类型拒绝；自建窗口通过真实注入、读取请求与无数据库写入拒绝的烟测。正式输出目录已重新构建。写入真实 MY 游戏仍待用户验收，未由代理代测。

- npm run build:native、npm run build：原生与前端构建。
- native/build/Release/wolf-database-test.exe：合成内存；不对称表维度、自定义名称、数字/字符串、分页、非法指针和歧义。
- npm run test:wolf：语义规则、RPC 边界、按焦点刷新及会话失效。
- npm run test:native：仅自建窗口，验证注入、握手、工具目录请求和 DLL unavailable 响应，不证明真实游戏读取成功。

用户自行完整重启 CTool 和游戏，进入地图/读档后检查：
1. 数据库浏览器能列出目录、正确行数、字段和值。
2. 金币来源和金额与菜单一致，金额变化后约一秒更新。
3. 自动识别不确定时选候选或在浏览器中手动绑定数字字段。
4. 失败时反馈诊断码、浏览器报错和游戏阶段。DLL 连接成功不等于数据读取成功。

写入验收：保存存档后完整重启 CTool 与游戏，进入地图，在控制台将金币改为一个容易核对的金额并点击应用；核对游戏菜单，再在游戏内消费，检查工具是否继续同步。编辑期间若游戏改变金币，工具应提示冲突而不覆盖。真实游戏仍由用户自行操作。
